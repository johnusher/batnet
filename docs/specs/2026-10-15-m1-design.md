# batnet milestone 1: design spec

**Status:** draft for review · **Date:** 2026-10-15 · **Covers:** milestone 1 (text)

This spec turns the design walk-through (sections 1–5) and decisions 0001–0016
into one description of what milestone 1 builds. The decisions in
[`knowledge/decisions/`](../../knowledge/decisions/) hold the reasoning; this
document says what to build. Where they disagree, this spec wins and the
decision gets a superseding record.

## 1. Goal

A household, a street or a village keeps talking when the power grid, the
mobile network and the internet are down. Each house runs a Raspberry Pi with
an open WiFi hotspot. People join from any phone, tablet or laptop and use a
WhatsApp-like app **in the browser**: no app download, no account with any
company. Houses link to each other over a batman-adv WiFi mesh nearby and over
Meshtastic LoRa radio further away (text only).

### Milestone 1 is done when (field test, 3–5 houses)

1. Phone A at house 1 sends text; phone B at a radio-only house receives it.
2. Phone C at a WiFi-linked house receives it too.
3. A plain Meshtastic app user holding the private channel key sees
   everyone-channel posts and can reply.
4. A node that was off catches up on what it missed when it comes back.
5. A new node takes one install (Imager) plus the phone set-up page.

### In milestone 1

House node, captive portal, accounts with admin approval, directory, groups and
the everyone channel, text chat, message priority (High/Normal/Low, admin
Alert), replicated log synced over batman-adv, text over LoRa through
meshtasticd, the "Neighbourhood (public)" group, the "Radios nearby" page,
no-phone mode on a Pi 4/5 screen (shared terminal, notice board), set-up with
QR join, the image and installer, health warnings; notifications in the app,
bedside mode, and a speaker, button and LED on the house Pi
([0018](../../knowledge/decisions/0018-notifications-and-house-speaker.md));
location per message from the phone or a GPS dongle on the node, and GPS time
([0019](../../knowledge/decisions/0019-location.md)).

### Not in milestone 1

Voice messages (M2, [0014](../../knowledge/decisions/0014-speech-pipeline.md)),
live calls (M3), the SDR scanner (M4), video, sensors, solar monitoring, the
text-only screen app for Zero/Pi 3, house-to-house software updates, native
phone apps, photos ([0020](../../knowledge/decisions/0020-photos.md)),
location tracking (M2) and location zones (later). The web app keeps a disabled mic button and greyed-out call button
with a "coming later" note, as in the mockup.

## 2. Hardware and roles

| Node | Board | Radios | Serves |
|---|---|---|---|
| House | Pi 4 or 5 (2 GB+) | built-in WiFi = hotspot, USB stick (MT7610U/MT7612U) = mesh, optional LoRa | ~40 (Pi 4) / ~60 (Pi 5) phones, estimated |
| House, one radio | any Pi with one usable WiFi radio | built-in = mesh, optional LoRa | its own screen ("mesh plus screen") or "hotspot only" |
| Pocket | Pi Zero 2 W | built-in = hotspot, LoRa | ~8 phones; links by LoRa only |
| Relay | Zero 2 W / Pi 3 | built-in = mesh | nobody; extends the mesh |
| Gateway | any of the above + LoRa | | bridges its WiFi group to the radio |

LoRa: RAK6421 + RAK13300 HAT (meshtasticd `official`) or Elecrow Meshstick
(USB). Parts and prices: [EU shopping list](../../knowledge/hardware/shopping-list-eu.md).

## 3. Architecture

```
 phones / laptops (browser)          Pi screen (kiosk, Pi 4/5)
          │ open WiFi "batnet · Miller House"   │ localhost
          ▼                                     ▼
 ┌──────────────────────────── house Pi ─────────────────────────────┐
 │ hostapd + dnsmasq (captive DNS)      cage + Chromium (if screen)  │
 │                                                                   │
 │ batnetd (pure Go, CGO_ENABLED=0)                                  │
 │   web: HTTPS app, captive-portal probes, WebSocket API            │
 │   auth: accounts, PINs, sessions, approvals                       │
 │   log: signed append-only log, folding into state (SQLite)        │
 │   sync: UDP broadcast + version vectors over bat0                 │
 │   lora: bridge to meshtasticd (TCP API), priority queue, duty     │
 │   setup: first boot, QR join, radio detection, health            │
 │                                                                   │
 │ batman-adv on the USB stick (bat0)        meshtasticd (SPI/USB)   │
 └───────────────────────────────────────────────────────────────────┘
          │ WiFi mesh (bat0)                         │ LoRa EU868
          ▼                                          ▼
     neighbouring houses, relays          gateways in other WiFi groups,
                                          plain Meshtastic users
```

One binary, `batnetd`, runs on every node; its role comes from the set-up
answers stored in `/etc/batnet/batnet.yaml`. It is cross-compiled for arm64
(Zero 2 W, 3, 4, 5) and ARMv6 (Zero W, relay only). Heavy work in later
milestones (speech, codecs, SDR) runs in helper processes over a local socket.

### Code layout

```
cmd/batnetd/          main, flags, role wiring
internal/log/         entry types, HLC, signing, folding, SQLite store
internal/sync/        bat0 broadcast, heartbeats, version vectors, range pulls
internal/lora/        meshtasticd client, envelope codec, fragments, queue, duty
internal/prio/        0-9 levels, ageing, rate limits
internal/web/         HTTP(S) server, captive portal, WebSocket API, kiosk mode
internal/auth/        accounts, PIN hashing, sessions, approvals
internal/setup/       first boot, QR join, radio detection, health checks
internal/mock/        mock village: in-process mesh and radio media
web/                  the app: HTML, CSS, JS modules, i18n strings (go:embed)
image/                Raspberry Pi OS Lite image build (pi-gen stage)
installer/            batnet.zip scripts for Windows, macOS, Linux
```

Storage: SQLite through `modernc.org/sqlite`. Crypto: Go standard library and
`golang.org/x/crypto` (ed25519, XChaCha20-Poly1305, argon2id, HKDF).

## 4. The replicated log

Every node keeps the whole log; state is what you get by folding it.

**Entry:** `(origin node ID, seq)` as the key, a hybrid logical clock stamp, a
type, a body, a priority level, and the origin node's ed25519 signature. Entries
never change. Between nodes, entries travel sealed with the village key
(XChaCha20-Poly1305, key derived with HKDF).

**Entry types in M1:**

| Type | Body |
|---|---|
| `node.announce` | node ID, house name, role, radios, software version |
| `house.join` / `house.approve` | a new house asks; an existing admin approves |
| `account.request` / `account.approve` / `account.deny` | name, home house, PIN hash (argon2id) |
| `account.update` | display name, PIN change, groups joined or left |
| `group.create` | name (e.g. Medical, Food) |
| `msg.post` | audience (`everyone`, `group:<id>`, `dm:<account>`), text, priority, optional location (lat, lon, accuracy in m, source `phone`/`node`) |
| `msg.read` | read marks, local to the house (not synced over LoRa) |
| `lora.sent` | Meshtastic packet ID ↔ entry key, so copies merge after a split |
| `alert` | admin Alert text (priority 9) |

Message order comes from the HLC, not the wall clock, so a Pi with a wrong
clock still orders correctly.

## 5. Sync over the WiFi mesh

* **Live:** a new entry is broadcast once over UDP on `bat0` (batman-adv floods
  broadcasts across the mesh).
* **Heartbeat** every 5 s: node ID, a hash of its version vector, its LoRa
  airtime used in the last hour.
* **Repair:** on a hash mismatch, two nodes exchange version vectors over HTTPS
  on `bat0` and pull the missing ranges, newest High first.
* A node returning from a power cut catches up the same way; a fresh SD card
  that rejoins the village (section 9) gets the whole log back from neighbours.

## 6. The LoRa bridge

batnetd talks to `meshtasticd` over its TCP API. One radio per gateway, preset
**LongFast**, EU868, two channels:

* **Private channel**, key derived from the village key. Carries batnet traffic.
* **Public channel** (Meshtastic's default LongFast). Shown in the app as
  "Neighbourhood (public)".

**What goes over the radio** (everything else stays on WiFi):

* posts whose audience includes a house in another WiFi group that a gateway
  can reach by radio;
* directory cards (who lives where) every 30 min, and changes;
* a compact version-vector **beacon** every 15 min per gateway, so other groups
  can ask for what they missed (recovery sends at most 8 entries per beacon);
* account and house approvals.

**Formats.**

* Everyone-channel posts go as plain Meshtastic text on the private channel,
  `Anna·Miller: text`, so Meshtastic users with the key can read and reply.
  High is shown as a leading `❗`, Alert as `⚠`.
* Direct and group messages use a compact binary envelope on the private
  channel (`PRIVATE_APP` port): version, type, 4-bit priority, entry key,
  audience, compressed text. Fragments of at most 200 bytes, at most 600
  characters of text (longer texts are shortened and marked "shortened for
  LoRa").
* Public posts are plain text on the public channel, never sealed.

**Who sends.** Each WiFi group may have several gateways. An entry is assigned
to one of the group's online gateways by its key (hash modulo the gateways,
from heartbeats). A gateway near its duty limit hands its queue to the next
one. `lora.sent` entries stop two gateways sending the same thing.

**Airtime.** Each radio keeps to 10% duty (360 s an hour) on 869.4–869.65 MHz.
batnetd tracks its own airtime and never asks meshtasticd to send beyond it.
Each radio has its own queue, so one radio at its limit never blocks another.

**Received from the radio:** batnet envelopes become log entries; plain text on
the private channel from a non-batnet node becomes an everyone-channel post
from "<node name> (Meshtastic)"; public channel text becomes a
"Neighbourhood (public)" post.

## 7. Message priority

As [decision 0015](../../knowledge/decisions/0015-message-priority.md):

* People choose **Normal** (default), **High** ("goes first over the radio and
  alerts people") or **Low** ("can wait"). The choice resets after sending.
* House admins can send an **Alert** to everyone; it shows as a red banner at
  the top of every phone and screen, with the admin's name.
* Levels 0–9: Alert 9, High 8, sync beacons 6, Normal 5 (+1 for direct
  messages, −1 for public posts and resends), Low 2, directory and
  housekeeping 1. Waiting raises a level one step per 20 minutes, up to 7.
* High is limited to **3 per person per hour** (admin setting).
* Applied in the LoRa queues, the WiFi repair order, and phone alerts (High
  plays a sound while the app is open; Low never alerts).
* On the local radio: Alert → `ALERT`, High → `HIGH`, Normal → `DEFAULT`, Low and
  background → `BACKGROUND` (Meshtastic's own queue).

## 8. The web app

**Delivery.** Plain HTML, CSS and JavaScript modules, no framework and no build
step, embedded in batnetd. Target: under 200 KB for the app shell; works on
phones from about 2018 (ES2017). English and German.

**Getting in.**

1. The phone joins the open WiFi "batnet · <house>". dnsmasq answers every DNS
   name with the Pi's address.
2. batnetd answers the operating systems' connectivity checks (Apple
   `hotspot-detect.html`, Android `generate_204`, Windows `connecttest.txt`) so
   the sign-in pop-up opens on `http://batnet/welcome`.
3. The welcome page explains there is no internet and that the pop-up can't use
   the microphone, and asks people to open **https://batnet** in their normal
   browser (copy button).
4. The browser shows a "not private" warning once (self-signed certificate per
   house, [0004](../../knowledge/decisions/0004-self-signed-https.md)); the
   welcome page shows how to continue on iPhone and Android.
5. Landing: **Help**, **Sign in**, **Create account**.

**Accounts.**

* Create: name and a 6-digit PIN. The request waits for the house admin (the
  phone shows "waiting for approval" and updates by itself).
* PINs are stored as argon2id hashes in the log, so people can sign in at any
  house. 5 wrong tries lock the account for 1 minute, doubling each time;
  admins can reset a PIN.
* Sessions: an HttpOnly, Secure, SameSite=Strict cookie lasting a year.

**Live connection.** One WebSocket per phone. The server pushes new entries
for the person's conversations and delivery states. The page keeps recent
messages in IndexedDB. Messages written out of range wait in an **outbox**
(IndexedDB) and send on reconnect. No service worker: browsers refuse to
register one on a page with a certificate warning
([browser limits](../../knowledge/research/browser-limits-offline.md)), so the
app is reloaded from the house Pi, which is local and fast.

**Screens** (as in the [mockup](https://johnusher.github.io/batnet/)):

* **Chats:** conversations with unread counts; Alert banner on top.
* **Conversation:** bubbles with delivery state ("✓ 3/7 houses", "via LoRa",
  "waiting for LoRa · 4 in queue", "shortened for LoRa"), the priority button,
  and a disabled mic until M2.
* **People:** by house, with reach chips: "Call + text", "Text via LoRa", "Out
  of reach".
* **Radios nearby:** Meshtastic nodes heard (name, distance if shared, signal),
  WiFi networks in range. Activity only, never content
  ([0009](../../knowledge/decisions/0009-scanner-activity-only.md)).
* **Settings** (fourth tab, for everyone): your name, change PIN, sign out,
  language, large text; **Radios nearby**; **Scan the air** (M4 preview in M1:
  the screen exists and shows Meshtastic and WiFi activity; the SDR band sweep
  with walkie-talkie, CB, ham, marine, LoRa and emergency-service bands arrives
  with the scanner, activity only); Help; and for house admins, **Admin**.
* **Admin:** join requests, Alert everyone, Add a house (QR), health warnings,
  High limit, screen mode.
* **Help:** what batnet is, the certificate warning, keeping the app open.

**Notifications** ([0018](../../knowledge/decisions/0018-notifications-and-house-speaker.md)).
A phone rings only while batnet is open: browsers offline have no service
worker and no push. So: sound and vibration (Android) per message, louder for
High, a siren for Alert, mute per chat, the unread count in the title; a
**bedside mode** that keeps the screen on and dimmed (Screen Wake Lock) while
charging. Settings: "Announce my messages on the house speaker" (off by
default), quiet hours, location source.

**Location** ([0019](../../knowledge/decisions/0019-location.md)). Off by
default; a 📍 button attaches the sender's position to one message (exact or
about 200 m); High messages ask, pre-ticked. Source in Settings: this phone
(Geolocation) or the node's GPS. Shown as distance and direction ("340 m
north-east of you") with coordinates and a map of the houses. Over LoRa the
position adds 8 bytes to the envelope.

**Limits shown to people, not hidden:** no notifications when the browser is
closed (keep the app open); the pop-up can't record; posts in "Neighbourhood
(public)" can be read by anyone with a Meshtastic radio.

## 9. Set-up, keys and running the network

**First boot.** The Pi opens the open WiFi "batnet · setup". The set-up page
asks for the language, the house name, the admin's name and PIN, the node's
role (house / relay on a pole / mesh plus screen, offered only where it fits),
and **start a new village** or **join one**.

**Village key.**

* New village: the Pi generates a random 32-byte key, stored only in
  `/var/lib/batnet` (mode 0600).
* Join: an admin of an existing house taps **Add a house**; their phone shows a
  QR code holding the village key, the village name and a one-time join token.
  The new Pi's set-up page scans it with the phone camera, or the admin reads a
  12-word code instead. Existing houses then see "New house: Weber. Approve?"
* Holding the key means reading village messages, so the QR is shown only on an
  admin's screen, for 2 minutes, and the help page says so.

**Node identity.** Each node generates an ed25519 key at first boot and signs
everything it originates.

**Radio detection.** batnetd reads each WiFi radio's supported modes (`iw`).
The built-in radio becomes the hotspot and a stick that supports mesh mode
carries batman-adv. With only one usable radio, set-up says so plainly and
offers "hotspot only" or "mesh plus screen". The LoRa board is recognised
(Meshstick by USB ID; the RAK HAT by its HAT EEPROM if it has one, else by
probing the SX1262 on SPI) and meshtasticd is configured for
EU868, LongFast and both channels.

**Time.** A Pi 4 has no clock that survives a power cut. A node with a GPS
dongle sets its clock from GPS and shares it in heartbeats. Otherwise, if the
clock is obviously wrong (before the release date), batnetd sets it from the
first phone that signs in; houses agree on time in heartbeats. Ordering never
depends on it (HLC).

**Health warnings** on the admin screen: "Your WiFi group has no radio",
"Radio near its airtime limit", "Low disk", "Hasn't heard from <house> for 2
hours", "Only one WiFi radio".

**Losing an SD card:** write a new card, join the village again, and the log
(accounts, messages) comes back from neighbouring houses.

## 9a. House speaker, button and LED

* **Speaker:** a USB speaker on any Pi (Pi 5 and Zero have no audio jack) or
  the Pi 4's jack. batnetd plays a chime and has espeak-ng (a separate process)
  say who a message is for and who sent it, for people who opted in; High says
  "Urgent message for Ben"; an Alert plays a siren and reads the full text.
  Quiet hours (default 22:00–07:00) silence all but High and Alert.
* **Button** (GPIO, pull-up, debounced): reads waiting announcements again;
  in no-phone mode it also wakes the screen.
* **LED** (GPIO): blinks while anyone in the house has unread messages.
* **GPS dongle** (USB, gpsd): sets the Pi's clock when it's wrong (before the
  HLC ever needs a phone) and gives the node's position.
* **ntfy** (optional): batnetd serves a per-person ntfy topic on the hotspot
  for Android phones with the ntfy app; it carries only "New message from
  <name>".

## 10. No-phone mode

As [decision 0016](../../knowledge/decisions/0016-no-phone-mode.md), M1 part:

* On a Pi 4/5 with a screen attached at boot, start cage + Chromium full-screen
  on `https://localhost`, trusting the house certificate.
* **Shared terminal** (default): sign in with name and PIN; signed out after 2
  minutes idle; a big Sign out button; keyboard-only use works.
* **Notice board** (admin setting): no sign-in, large type, rotating through
  alerts, the everyone channel and "Neighbourhood (public)".
* A laptop on the Pi's Ethernet port gets an address by DHCP and the same app.
* Nothing starts without a screen.

## 11. Image and installer

As [decision 0013](../../knowledge/decisions/0013-one-download-installer.md):

* An image built on Raspberry Pi OS Lite (arm64) with batnetd, meshtasticd,
  batman-adv, hostapd, dnsmasq, cage and Chromium. Published as a release asset
  `batnet.zip` at
  `https://github.com/johnusher/batnet/releases/latest/download/batnet.zip`.
* The zip holds the image, `Install on Windows.bat`, `Install on Mac.command`,
  `install-linux.sh` and `READ ME FIRST.txt`. The scripts open Raspberry Pi
  Imager with the batnet image chosen; they never write to a disk themselves.
* For a Pi already on Raspberry Pi OS: one command fetches and runs the
  release's `install.sh`.
* Releases are signed (ed25519 release key, kept offline, never in the repo).
  In M1, updating means writing a new card or copying an update file from a USB
  stick.

## 12. Security and privacy

* **Who can read what:** anyone with the village key reads all village traffic;
  anyone with a Meshtastic radio reads "Neighbourhood (public)". Strangers in
  WiFi range can join the open hotspot but see only the welcome page until an
  admin approves them.
* **Integrity:** entries are signed by their origin node; houses join only with
  an existing admin's approval.
* **The open hotspot** isolates clients from each other (hostapd
  `ap_isolate`), and only batnetd's ports are reachable.
* **Abuse:** PIN lockout, High rate limit, Alerts admin-only and named,
  admins can remove accounts.
* **The repo is public:** keys, PSKs and personal data never go in it
  ([secret hygiene](../../knowledge/security/secret-hygiene.md)).

## 13. Failure handling

| Situation | Behaviour |
|---|---|
| House loses power | Its phones lose the app; messages to it wait in the log of other houses and arrive on return |
| WiFi group split | Each part keeps working; repair merges them when they reconnect |
| Radio at its duty limit | Its queue waits (highest priority first); another gateway in the group takes over |
| No radio in a WiFi group | Works inside the group; admin warning; messages to other groups wait |
| Phone out of range | Outbox; sends on reconnect |
| Wrong clock | HLC ordering; time corrected from phones |
| Disk full | Oldest Low messages' bodies pruned first (keys kept); admin warning |
| meshtasticd stops | batnetd restarts it (systemd) and shows "radio offline" |

## 14. Testing

1. **Unit tests** (Go): HLC, signing, folding, envelope codec, fragments,
   priority and ageing, airtime and duty accounting, PIN lockout.
2. **Mock village** (`batnetd -mock`): several nodes in one process or several
   processes on one machine, with an in-memory mesh medium and a radio medium
   using the same airtime, duty and loss rules as the
   [village simulator](../../prototypes/village-sim/). Scenario tests: delivery
   within 10 minutes, catch-up after an outage, High before Normal, partition
   and merge, a WiFi group without radio.
3. **Browser tests** (Playwright, Chromium and WebKit) against the mock
   village: sign-up, approval, chat, outbox, Alert banner, kiosk mode.
4. **Bench**, 2–3 Pis: real dongles and HATs; captive portal pop-up on iPhone,
   Android and a laptop; the microphone after the certificate warning on a real
   iPhone and Android phone (gates M2 and M3); power draw of the WiFi stick and
   a pocket node on a power bank; desktop pop-up notifications past the
   certificate warning; how long Android keeps the connection in a background
   tab; Wake Lock on iOS; the speaker, button and LED on each Pi model.
5. **Field**, 3–5 houses: the five done-when checks in section 1, delivery
   times compared with the simulator. Written up in `knowledge/tests/` with no
   places, names or device IDs.
6. **CI** (GitHub Actions): `go test`, mock-village scenarios, gitleaks,
   okflint, the Pages deploy of the simulator.

## 14a. Simulating the real code

The village simulator runs **batnet's real Go code**, not a copy of its logic.

* **Virtual time.** The core reacts to events (a packet arrived, a timer fired)
  instead of owning goroutines and tickers; a small driver feeds it real time on
  a Pi and a virtual clock in the simulator. Same seed, same run: any bug found
  in a simulation can be replayed exactly.
* **What is modelled, in Go (`internal/mock`):** the physical world: WiFi range
  per Pi model and radio, multi-hop batman-adv flooding, a shared WiFi channel
  whose loss grows with load, LoRa airtime, duty and collisions (from plan 3),
  power cuts, Pi capacity, people's behaviour. One model, replacing `sim.js`'s
  over time.
* **Scenarios** are JSON files in `scenarios/`: houses, hardware, positions,
  scripted events ("everyone within 800 m of the school posts within 30 s"),
  and checks ("every house in a WiFi group holds every message within 10
  min", "no entry lost", "LoRa within duty").
* **Two runners, same code:** `batnetd -sim scenarios/bang.json` runs headless
  and exits non-zero when a check fails (CI runs every scenario on every push);
  the simulator page loads the same engine compiled to WebAssembly
  (`batnet.wasm`, about 1 MB compressed) and draws it live or sped up.
* As plans land (LoRa bridge, priority, accounts, notifications), their code
  joins the simulation; the page offers "model (JavaScript)" and "real batnet
  code" engines until the Go model covers everything.

## 15. Risks to check first

| Risk | Check | If it fails |
|---|---|---|
| Captive pop-up or certificate flow confuses people | bench test with non-technical users | simplify the welcome page; consider plain HTTP for text-only M1 |
| MT7610U stick unreliable in mesh mode on Pi OS | bench: 24 h batman-adv run | try MT7612U or AR9271 |
| meshtasticd TCP API gaps (priority, airtime) | spike: send/receive with priority from Go | track airtime only in batnetd |
| Chromium kiosk memory on a 2 GB Pi 4 | bench | recommend 4 GB for screens |
| LoRa congestion at events | simulator stress scenario; event presets | Low batching, second radio ([0008](../../knowledge/decisions/0008-longfast-single-radio.md)) |
